## Initial conclusion
The recovered stash was valuable and restored the key missing safeguards, but it was not the whole job. The branch contained the likely core fix, while proof, bounded verification, and one small correctness refinement were still missing.


## Root cause confirmation
### Primary amplification path
1. **GatewayConnector forwards raw assistant text snapshots unchanged**
   - `backend/src/services/GatewayConnector.ts` emits `payload.data?.text` directly as `agent:stream.text`.
   - There is no delta extraction at the connector layer.

2. **Those assistant snapshots are cumulative in practice**
   - The existing frontend fix in commit `f314ad7` (`fix(live-session): coalesce cumulative stream updates`) already proves the dashboard was seeing growing assistant snapshots rather than pure deltas.
   - The new in-memory reproduction test shows the Discord thread path would also over-append without a delta reducer.

3. **Pre-recovery DiscordThreadService appended assistant text naively**
   - Before `d7cd911`, `handleAgentStream(...)` called `appendText(state, event.text)` directly.
   - When the gateway emitted `Hello`, then `Hello world`, then `Hello world!!!`, the thread buffer would become cumulative junk rather than the final bounded text.

### Secondary amplifiers
4. **Listener wiring could multiply the same stream event**
   - Pre-recovery `setGatewayConnector(...)` attached a fresh `agent:stream` listener without removing the old one.
   - If wiring happened more than once, each assistant event could be processed multiple times.

5. **Outbound thread posting had no duplicate brake**
   - Before the recovered safeguard, identical rendered messages could be posted repeatedly to the same Discord thread.
   - This turned replayed or duplicated upstream events into visible repeated thread spam.

### Not the root cause
6. **Poll/steer flow is not the autonomous loop source**
   - `pollThreadReplies(...)` advances `lastMessageId` and uses `after` on subsequent reads.
   - It only forwards non-bot text from authorized users.
   - The service's own steering acknowledgement is bot-authored, so it is filtered out and does not recursively steer itself.
   - Polling can add traffic when a human replies, but it is not the self-sustaining loop.

## Final diagnosis
The real thread-loop bug was not one single defect. It was a stacked amplification chain:

- cumulative assistant snapshots arriving from the gateway path,
- naive append behavior in `DiscordThreadService`,
- possible duplicate `agent:stream` listener registration,
- and no outbound duplicate suppression.

The poll/steer path is adjacent behavior, but not the root loop source.

## Rollout guidance
### Recommendation
- **Do not add a new permanent runtime gate in this patch.**
- **Production re-enable is reasonable with a controlled canary, not a blind all-clear.**

### Why no new gate now
- The bug was inside the Discord thread streaming path itself, and the fix is tightly scoped there.
- The new coverage already exercises the risky edges directly: cumulative assistant snapshots, duplicate listeners, outbound duplicate suppression, retry behavior, and steer preservation.
- Adding a fresh feature flag right now would increase config surface and rollout complexity without addressing a new unknown root cause.

### Safer rollout shape
1. Deploy the patch normally.
2. Use **one** interactive task as a canary.
3. Watch backend logs for:
   - repeated `Suppressed duplicate outbound thread message` warnings
   - repeated identical assistant chunks for the same thread
   - unexpected repeated steer acknowledgements
4. Verify the Discord thread shows bounded readable updates rather than cumulative replay.
5. If the canary is clean, treat production re-enable as safe.

### If an emergency brake is needed later
If operations still want a kill switch, the right shape is a **small env-gated stream brake** around assistant/tool streaming only, not around thread creation or steering. That preserves the thread as a communication surface while disabling the risky live-output path.

Suggested future flag only if needed:
- `DISCORD_THREAD_STREAMING_ENABLED=false`

But that is **not required** for this fix set to be mergeable.
